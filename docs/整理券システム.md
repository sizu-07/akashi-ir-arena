# 整理券システム 運用・配置手順

## 構成

整理券機能は、教室内で動く既存ゲームサーバーから分離している。

- 外部整理券サーバー: 来場者受付、待機列、4席割当、運営操作、入場QR、監査履歴を管理する。
- 教室内ゲームサーバー: ゲーム状態を管理し、開始・停止・再開・終了イベントを外部整理券サーバーへ送る。
- ゲームイベントは `data/*/ticket-outbox.json` に残し、送信に失敗した場合は同じイベントIDで再送する。
- 整理券サーバーは受信済みイベントIDを保存し、同じイベントを1回だけ反映する。
- 1枠は15分固定とし、4席は組を分割せずに後続の入れる組で自動充当する。
- 受付では参加人数分のニックネームを登録し、呼出中の枠の4名をゲーム画面のプレイヤー名へ反映する。

## 起動方法

Node.js 20以上が必要。

利用者が操作する起動ファイルは次の2本だけである。どちらもローカルのゲーム管理サーバーだけを起動し、ブラウザーでゲーム運営画面を自動的に開く。

| 用途 | 起動ファイル |
|---|---|
| PCだけで一連の操作を試す | `起動_デモ.cmd` |
| 実機4台を接続して運営する | `起動_本番.cmd` |

整理券の受付・表示・運営・入場読取は公開サーバーで動作する。整理券をローカルでも起動すると正本が2つに分かれるため、通常運用ではローカル整理券サーバーを起動しない。

| 画面 | 開き方 |
|---|---|
| ゲーム運営 | `http://localhost:8080/` |
| 整理券運営 | ゲーム運営画面上部の「整理券運営（公開）」 |
| 来場者受付 | ゲーム運営画面上部の「来場者受付」 |
| 入場読取 | ゲーム運営画面上部の「入場QR読取」 |

ゲーム運営画面と整理券運営画面の上部には共通タブがあり、別サーバー上の画面でも往復できる。公開サーバー側へゲーム運営画面のURLを引き継ぐため、同じ運営端末で開く。

スマートフォンのカメラ読取は、外部公開時はHTTPSで利用する。ローカル確認では `localhost` が必要で、LAN内の平文HTTPアドレスではブラウザーがカメラを拒否する場合がある。

## ゲーム管理サーバーと接続する

既存の `config/local.json` に次を追加する。

```json
{
  "ticketServerUrl": "https://tickets.example.com",
  "ticketServerApiKey": "外部サーバーのTICKET_GAME_API_KEYと同じ値"
}
```

URLまたはキーを設定しなければ、既存ゲーム機能は従来どおり動作し、整理券連携だけが無効になる。

対応イベントは次のとおり。

| ゲーム状態の変化 | 送信イベント | 整理券側 |
|---|---|---|
| 待機・停止から試合中 | `GAME_STARTED` / `GAME_RESUMED` | 呼出中の枠を体験中へ変更。呼出操作がない場合は先頭枠を使用 |
| 試合中・カウントダウンから停止 | `GAME_PAUSED` | 対象回を呼出状態へ戻し、遅延を加算 |
| 試合終了 | `GAME_ENDED` | 対象枠と整理券を完了へ変更し、次枠を自動呼出 |

## 運営手順

1. `/operator` へログインし、「主操作端末」であることを確認する。
2. 全体遅延、呼出猶予、最大待機組数を設定する。1枠は15分固定である。
3. 「受付開始」を押し、`/register` のURLをQRコードとして教室前へ掲示する。
4. 画面上部の待機列図で4席の自動割当と空席を確認し、「次の4名を呼び出す」を押す。
   各カードでは整理券番号ごとに色付きラベルを表示し、同じ色の座席が同じ登録グループであることを示す。
5. `/scanner` で来場者のQRコードを読み取る。成功はサーバー側で1回だけ記録される。
   上部の待機列カードは、一部を確認すると「入場中 ○/○」、全員を確認すると緑色の「全員入場済み」に変わる。
6. ゲーム運営タブでゲームを開始・終了する。開始時に参加者名がゲームへ反映され、終了時に待機列が進んで次枠が自動呼出される。
7. 呼出中の来場者が現れない場合は、待機列図の下で対象の登録グループを確認し、その組の「この組をスキップ」を押す。空席には後続の入れる組が自動補完され、スキップした組は整理券一覧から待機列へ戻せる。
8. スキップした組が後から来場した場合や、誤ってゲーム終了にした枠を再実施する場合は、「過去枠」から対象枠を選んで呼び戻す。別の枠を呼出中なら、その枠はスキップされて選択した過去枠へ切り替わる。体験中の枠がある場合や、現在の呼出枠に入場済みの人がいる場合は切り替えられない。
9. 取消、来場なし、入場取消、枠のスキップ・呼戻しでは理由を入力する。
   整理券一覧の操作ダイアログには、その整理券の現在状態で実行できる操作だけが表示される。失敗理由や必須入力の不足はダイアログ内に表示される。
10. ページ下部の「全枠の順番・履歴」を横スクロールし、終了済みから将来の予約までがカード形式で枠番号順に並んでいることを確認する。
11. 終了後に履歴CSVを保存し、定めた保存期間の後でサーバー上のデータを削除する。

呼出中または体験中の枠がある間は、次枠の呼出ボタンが無効になる。二重呼出状態が保存されていた場合は、再起動時に体験中、次に入場確認済み、最後に受付順の優先度で1枠へ自動修復する。

一度以上の枠を実施した後、呼出中・体験中・予約済みの枠がすべてなくなった状態で新しい整理券が登録された場合は、その新規枠を自動的に呼出中へ変更する。開場直後の最初の登録は4席への後続充当を可能にするため自動呼出しせず、通常どおり運営が呼出操作を行う。

自動呼出しされた枠が4人未満の場合、その枠が呼出中である間は、後続登録のうち残席に入る組を受付順に追加する。既に呼び出した組は移動せず、同じ組も分割しない。例えば登録人数が `2 → 4 → 1 → 3 → 1` の順なら、呼出中枠は `2 + 1 + 1 = 4人`となり、4人組と3人組は後続枠に残る。ゲーム開始後は枠を変更しない。

スキップは枠全体ではなく、整理券として登録されたグループ単位で行う。入場確認済みのグループはスキップできないため、対象整理券の「入場処理を取り消す」を理由付きで実行してから操作する。全グループがスキップされ、補完できる後続組もない場合だけ、その枠自体をスキップ済みにする。過去枠から呼び戻せるのは「スキップ済み」または「終了済み」の枠で、終了済みを選ぶ場合は再実施であることを確認する警告が表示される。

ゲーム運営画面の「整理券」が `同期済み`、整理券運営画面の表示が `ゲーム連携中` であることを開場前に確認する。`未設定` の場合は `config/local.json` の公開URLとAPIキーを確認して再起動する。`未同期` の場合は、教室ネットワークから公開URLへ接続できるか確認する。

## 外部配置

`Dockerfile.ticket` でコンテナ化できる。保存先は次のいずれかを選ぶ。

1. 無料優先: Render無料WebサービスとSupabase無料Postgresを組み合わせる。
2. 単純さ優先: 永続ボリュームを付けられる有料Nodeホストでファイル保存する。

### 無料構成の登録と配置

外部公開にはRenderアカウントとSupabaseアカウントが必要。アカウント作成と秘密鍵の取得は利用者本人が行う。

1. Supabaseでプロジェクトを1個作成し、SQL Editorで `deploy/supabase.sql` を実行する。
2. Project URLとSecret Keyを控える。Secret KeyはブラウザーやGitへ置かない。
3. RenderでこのGitHubリポジトリを接続し、`render.yaml` のBlueprintを作成する。
4. Renderの秘密環境変数に下表の値を登録する。
5. 最初の配置後に発行された `https://...onrender.com` URLを `PUBLIC_ORIGIN` に設定して再配置する。
6. `/operator` へログインし、教室前掲示QRを印刷する。
7. 教室PCの `config/local.json` に同じ公開URLとゲームAPIキーを設定する。

Render無料サービスは無通信時に停止する。運営画面または来場者画面のWebSocketは30秒ごとに小さいハートビートを送り、開場中の停止を避ける。Render自身は無料サービスを本番用途として推奨しておらず、任意再起動や起動待ちの可能性は残る。開場前に運営画面を開いて疎通を確認し、紙整理券への切替手順も用意する。

### 環境変数

| 変数 | 必須 | 内容 |
|---|---:|---|
| `PORT` | 任意 | HTTPポート。既定8787 |
| `PUBLIC_ORIGIN` | 必須 | 末尾スラッシュなしの公開HTTPS URL |
| `TICKET_OPERATOR_PASSWORD` | 必須 | 12文字以上。十分にランダムな値 |
| `TICKET_GAME_API_KEY` | 必須 | 24文字以上。十分にランダムな値 |
| `SUPABASE_URL` | 無料構成 | Supabase Project URL |
| `SUPABASE_SECRET_KEY` | 無料構成 | `sb_secret_` で始まるサーバー専用Secret Key |
| `TICKET_DATA_DIR` | ファイル構成 | 永続ボリューム上の絶対パス |

起動コマンドは `node apps/ticket-server/main.mjs`、ヘルスチェックは `/health` とする。WebSocketを許可し、単一インスタンスで運用する。Supabase利用時も処理中の待機列はメモリーにあるため、複数インスタンス化は禁止する。

無料Webサービスの一時ファイル領域へ `TICKET_DATA_DIR` を置いてはならない。Supabaseを設定した場合、整理券状態と監査イベントは各操作の応答前にSupabaseへ保存される。

## セキュリティと障害時

- 公開QRは `/register` のURLだけを含める。
- 整理券URLと入場QRには別々の192ビット相当ランダムトークンを使う。
- 運営Cookieは `HttpOnly`、`SameSite=Strict`。`PUBLIC_ORIGIN` がHTTPSなら `Secure` を付ける。
- 運営変更APIはCSRFトークンと主操作端末の所有権を確認する。
- ゲーム連携はBearer APIキー、イベントID、再送番号を使用する。
- ゲーム開始・終了イベントには対象枠IDを必須とし、対象枠IDのない古い再送イベントや、体験中ではない枠への終了イベントは反映しない。
- 外部サーバーが応答しない場合、入場読取は成功表示を出さない。
- 来場者画面はWebSocket切断を明示し、5秒間隔の再取得へ切り替える。
- データ削除は、サーバー停止後に `TICKET_DATA_DIR` 内の `tickets.json` と `ticket-events.jsonl` をバックアップしてから削除する。

## 現段階の制約

- 画面外通知（Web Push、LINE、メール）は未実装。
- 同一人物による複数登録は、個人情報を取得しない方針と両立する確実な判定方法がないため未実装。
- 呼び出し名の自動不適切表現判定は誤判定対策が必要なため未実装。運営一覧から変更・取消を行う。
- 現在の公開構成は単一会場・Render単一インスタンス向け。複数会場や複数インスタンスでの同時運営には、割当処理をデータベーストランザクションへ移す必要がある。
